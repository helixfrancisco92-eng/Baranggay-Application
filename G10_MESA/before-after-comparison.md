## 1. Purpose and Methodology

The primary goal of before-and-after maintenance comparison is to provide quantifiable, empirical evidence that database maintenance operations (`VACUUM` and `ANALYZE`) successfully achieved their technical objectives:
1. **Reclaiming Dead Tuples:** Verifying that space occupied by deleted or updated row versions was freed for reuse.
2. **Refreshing Optimizer Statistics:** Ensuring that `pg_statistic` contains current row counts and value distributions so that the query planner chooses optimal execution paths.
3. **Tracking Maintenance Timestamps:** Verifying that `last_vacuum` and `last_analyze` reflect the recent maintenance event in `pg_stat_user_tables`.

> [!IMPORTANT]
> **Academic Integrity & Quality Standard:**
> In accordance with COMP 018 requirements, no synthetic or fabricated measurements are manufactured. If live historical metrics have not yet been recorded due to execution environment constraints (such as pending credential prompts), they are designated as **`Awaiting Live Execution Capture`** or **`Not recorded`**, alongside the exact commands used to record them.

## 3. Explaining Observable Changes & System Limitations

### 3.1 What Measurably Changes
1. **`last_vacuum` and `last_analyze`:**
   In PostgreSQL, these catalog columns in `pg_stat_user_tables` are updated immediately upon completion of manual `VACUUM` and `ANALYZE`.
2. **`n_dead_tup`:**
   For tables where records were modified or deleted, `n_dead_tup` drops to 0 (or near 0), demonstrating that dead tuples have been purged from the active heap and registered in the Free Space Map.
3. **`n_mod_since_analyze`:**
   Resets to 0 immediately upon running `ANALYZE`.

### 3.2 What Does NOT Reset (Cumulative Counters)
* `seq_scan`, `idx_scan`, `n_tup_ins`, `n_tup_upd`, and `n_tup_del` are cumulative statistics collected since the database cluster was initialized or since the last administrative call to `pg_stat_reset()`.
* Therefore, running `VACUUM` or `ANALYZE` does not set `seq_scan` to zero; rather, it allows new queries to use more efficient scan paths.

### 3.3 Test Database Dataset Limitations
* On small development databases (e.g. 60 orders and 30 menu items), queries already execute in a fraction of a millisecond.
* A DBA should not make unfounded claims of "10x query speedups" on a database containing 60 rows, because execution time is already bounded by CPU instruction cycles. The true performance value of `VACUUM` and `ANALYZE` manifests when transaction volume scales into thousands and millions of rows.
