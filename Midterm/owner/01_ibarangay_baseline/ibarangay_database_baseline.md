## 1. Executive System Profile & Architectural Purpose

iBarangay is a digital municipal governance platform engineered to modernize citizen document requests and public administrative processing at the barangay level (the primary political unit in the Philippines). The application enables community residents to request essential certifications (such as Barangay Clearance, Certificate of Indigency, Certificate of Residency, and Barangay Business Clearance), submit supporting requirements, and track request lifecycles. Barangay administrative officers and staff process requests, approve or reject applications, record processing fees, and archive immutable transaction histories.

## 2. Relational Database Schema & Table Inventory

The iBarangay relational schema is version-controlled using **Flyway Database Migrations** under `src/main/resources/db/migration/`:
- `V1__initial_schema.sql`: Core 7 tables, foreign key constraints, default timestamps, and status flags.

## 3. Constraints, Identity Sequences & Indexing Baseline

1. **Automatic ID Generation (Identity Sequences):**
   - Per Flyway migration `V2__improve_database_structure.sql`, all primary keys utilize modern SQL-standard `GENERATED BY DEFAULT AS IDENTITY`.
   - Underlying PostgreSQL sequences created automatically:
     - `admins_admin_id_seq`
     - `citizens_citizen_id_seq`
     - `document_types_document_type_id_seq`
     - `requirements_requirement_id_seq`
     - `document_requests_request_id_seq`
     - `request_status_history_history_id_seq`
   - Explicit `SELECT setval(...)` synchronization statements in V2 guarantee that sequence generators remain aligned with seeded data.
2. **Referential Integrity & Cascades:**
   - Associative table `document_type_requirements` cascades deletions from master lookups (`ON DELETE CASCADE`).
   - `request_status_history` cascades deletion when a parent request is deleted (`ON DELETE CASCADE`).
   - Parent master tables (`citizens`, `document_types`, `admins`) utilize default `RESTRICT` behavior when referenced by `document_requests`.
3. **Application Entity Validation & Business Rules:**
   - Enforced status lifecycle: `PENDING` $\rightarrow$ `APPROVED` or `REJECTED` $\rightarrow$ `READY` $\rightarrow$ `RELEASED` or `CANCELLED`.
   - Rejection remarks required: When status is `REJECTED`, business logic requires remarks explaining the cause for rejection.

## 4. Role-Based Access Control Baseline (Activity 4)

In accordance with `iBarangay-user-role.md` and Activity 4 Access Control specifications, iBarangay implements a two-tier security paradigm:
1. **Tier 1 (Application Level):** Distinguishes end-user personas (Administrator, Barangay Staff, Citizen/Resident) enforced via server-side session checks and Spring Security controllers.
2. **Tier 2 (Database Engine Level):** All application instances connect through a dedicated, non-superuser service account governed by least-privilege PostgreSQL grants:

| Role Name | Role Type | Login Allowed | Database Membership / Granted Privileges |
|---|---|:---:|---|
| `ibarangay_runtime_grp` | Group Role | `NO` | - `CONNECT ON DATABASE "PPGG_projectdb"`<br>- `USAGE ON SCHEMA public`<br>- `SELECT` on all 7 tables (`citizens`, `admins`, `document_types`, `requirements`, `document_type_requirements`, `document_requests`, `request_status_history`)<br>- `INSERT, UPDATE` on operational tables (`citizens`, `document_requests`)<br>- `INSERT` on audit table (`request_status_history`)<br>- `USAGE, SELECT` on all identity sequences<br>- **Strictly Denied:** `DELETE` on all tables; `UPDATE` on audit history; DDL modifications. |
| `ibarangay_app` | User Account | `YES` | - Inherits `ibarangay_runtime_grp`<br>- Dedicated connection credentials used by Spring Boot `application.properties`. |

## 5. Performance, Maintenance & Monitoring Baseline (Activity 5)

1. **Buffer Cache & Storage Profile:**
   - Active database size: ~8,950 kB to 9,200 kB on PostgreSQL 18.6.
   - Buffer cache hit ratio: Consistently maintained at **99.85%+** across local testing.
2. **Query Performance:**
   - Primary request search queries utilize indexed primary key joins (`document_requests.citizen_id = citizens.citizen_id`).
   - Average response time for standard portal dashboards: **< 1.2 ms**.
3. **Routine Maintenance Protocol:**
   - Documented procedure mandates regular `ANALYZE` and `VACUUM` execution on high-transaction tables (`document_requests`, `request_status_history`) to prevent dead-tuple accumulation resulting from status updates.

## 6. Backup, Recovery & Disaster Readiness Baseline (Activity 6)

1. **Backup Strategy:**
   - Automated logical exports utilizing PostgreSQL custom compressed format:
     ```powershell
     pg_dump.exe -U ibarangay_app -h localhost -p 5432 -Fc -d PPGG_projectdb -f "backups/PPGG_projectdb_backup.dump"
     ```
2. **Restoration Verification Procedure:**
   - Restoration is validated into an isolated disposable test database:
     ```powershell
     createdb -U postgres -h localhost -p 5432 PPGG_projectdb_disposable
     pg_restore.exe -U postgres -h localhost -p 5432 -d PPGG_projectdb_disposable "backups/PPGG_projectdb_backup.dump"
     ```
   - Automated post-restore verification scripts confirm record parity across all 7 tables and sequence continuity.

## 7. Known Architectural Limitations & Baseline Gaps

1. **Authentication Secret Storage:** The initial `admins` table definition includes `username` and `role`, but omitted a `password_hash` column in early migrations. The system relies on Spring Security memory/env configurations or external authentication adapters.
2. **Citizen Portal Login:** The `citizens` table stores demographic records but lacks separate authentication credentials (`password_hash`), meaning resident document tracking currently relies on transaction reference IDs or resident contact matching.
3. **Audit History Cascade:** Similar to peer projects, `request_status_history` utilizes `ON DELETE CASCADE` referencing `document_requests`. While the runtime role `ibarangay_runtime_grp` is denied `DELETE` privileges, hard deletes executed by superusers would purge audit history.
