## 2. Query Planner Statistics Maintenance (`ANALYZE`)

### 2.1 Technical Purpose & Planner Mechanism

PostgreSQL's cost-based query optimizer (CBO) relies on statistical distributions stored in `pg_statistic` to calculate row estimates (`reltuples`), selectivity, and execution costs. Over time, transactional inserts and status transitions cause statistics to become stale. 

Executing `ANALYZE`:
- Reads a random sample of table pages (governed by `default_statistics_target = 100`).
- Computes null fractions, average column byte widths, distinct values (`n_distinct`), Most Common Values (MCVs), and equi-depth quantile histograms.
- Updates `reltuples` and `relpages` in `pg_class`.
- Logs `last_analyze` and increments `analyze_count` in `pg_stat_user_tables`.
- **Locking Level:** Obtains only a lightweight `ShareUpdateExclusiveLock`, which permits concurrent `SELECT`, `INSERT`, `UPDATE`, and `DELETE` operations without interruption.

## 3. Storage Reclamation & Vacuuming (`VACUUM`)

### 3.1 Technical Purpose & Operational Rules

In PostgreSQL's Multi-Version Concurrency Control (MVCC) architecture, an `UPDATE` or `DELETE` statement does not physically overwrite or immediately delete data. Instead:
- An `UPDATE` marks the old tuple as dead (setting `t_xmax` to the current transaction ID) and writes a new tuple version into the table page.
- A `DELETE` marks the tuple as dead.

Dead tuples consume page space until reclaimed. Standard `VACUUM`:
- Scans heap pages, locates dead tuples whose `t_xmax` precedes the oldest active transaction, and marks their line pointers (`ItemId`) as unused.
- Updates the Free Space Map (FSM) so future `INSERT` and `UPDATE` statements can reuse those page slots.
- **Rule 1 — Standalone Execution:** `VACUUM` cannot run inside a transaction block (`BEGIN ... COMMIT`). It must be executed as an independent SQL statement.
- **Rule 2 — Non-Blocking Operation:** Standard `VACUUM` takes only a `ShareUpdateExclusiveLock`. It does not lock tables against reads or writes.
- **Rule 3 — VACUUM FULL Prohibition:** `VACUUM FULL` was strictly avoided. `VACUUM FULL` rewrites the entire relation into a new disk file, holding an exclusive table lock (`AccessExclusiveLock`) that blocks all application operations.

## 5. Maintenance Permission Boundary & Error Investigation

### 5.1 Permission Boundary Test

When maintenance was attempted under the runtime application user (`campussafe_app`):

```sql
SET ROLE campussafe_app;
VACUUM public.hazard_report;
```

**PostgreSQL Diagnostic Response:**
```text
WARNING:  permission denied to vacuum "hazard_report", skipping it
VACUUM
```

### 5.2 Technical & Security Explanation

1. **Root Cause:** PostgreSQL 14+ enforces that `VACUUM` and `ANALYZE` require table ownership or superuser status. Because `campussafe_app` is an application login account and does not own `hazard_report` (which is owned by `postgres`), PostgreSQL issues a warning and safely skips the table.
2. **Security Compliance:** This boundary is correct and expected under the Principle of Least Privilege. Application runtime accounts must never hold table ownership. Granting ownership would allow the application account to drop tables or alter schema definitions.
3. **Operational Resolution:** Maintenance must be executed by:
   - Automated PostgreSQL `autovacuum` worker processes, OR
   - Scheduled DBA cron/task jobs running as `postgres` or an authorized DBA account.
